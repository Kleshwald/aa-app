# MCP для Cursor — пилот на 1С:Предприятие 8.5

**Статус:** playbook · v1.0 · для пилота 8.5 Agent Academy · в связке с [DECISION-frontend-platform.md](./DECISION-frontend-platform.md), [DESIGN-1C-85.md](./DESIGN-1C-85.md), память `project_platform_fork_1c85`.

Инструкция по подключению MCP-серверов к Cursor, чтобы Claude при работе
с конфигурацией на платформе 8.5 видел метаданные, справку и мог проверять код.

**Цель:** повысить качество AI-генерации кода 1С с ~20-30% (вслепую)
до ~60-80% (с контекстом) на задачах пилота 8.5:
- адаптация форм под новый интерфейс 8.5
- HTTP-сервисы по api-contract.yaml
- рутинные обработки и запросы

> ⚠️ Цифра 60-80% — **гипотеза, а не факт**. Именно её проверяет метрика пилота (§8).
> Линчпин качества — доступность справки **именно 8.5** (§0.1); без неё ИИ тихо
> откатывается на API 8.3. Это риск, а не данность.

---

## 0. Важная оговорка про 8.5

Экосистема MCP для 1С выросла на платформе 8.3. Платформа 8.5 вышла недавно,
поэтому **перед стартом проверь по каждому серверу**:

1. **Справка платформы.** Серверы типа docsearch индексируют справку конкретной
   версии. Нужна выгрузка справки **8.5** (файлы .hbk из дистрибутива 8.5 или
   онлайн-справка its.1c.ru). Если сервер поддерживает только 8.3 — ИИ будет
   советовать старый API и не знать новых свойств интерфейса 8.5.
2. **Формат выгрузки конфигурации.** Выгрузка в XML из конфигуратора 8.5 может
   иметь новые свойства метаданных (темы, карточки, новая оконная система).
   Парсеры метаданных должны их не ломать (в худшем случае — игнорировать).
3. **Синтакс-чек.** BSL Language Server обновляется — взять свежую версию,
   проверить changelog на поддержку новшеств 8.5.

Если какой-то сервер не дружит с 8.5 — это не блокер: запускай его на выгрузке
в режиме «как для 8.3», а специфику 8.5 закрывай справкой (пункт 3 ниже).

## 1. Предусловия (сделать до настройки MCP)

- [ ] **Dev-база на 8.5** развёрнута (копия рабочей, обезличенная).
      НИКОГДА не подключать MCP с выполнением кода к продакшн-базе.
- [ ] **Выгрузка конфигурации в файлы**: Конфигуратор → «Выгрузить конфигурацию
      в файлы» (XML) в папку `1c-src/` внутри проекта. Это главное:
      без выгрузки ИИ не видит вашу конфигурацию.
      Обновлять выгрузку после каждого изменения конфигурации (можно скриптом).
- [ ] **Справка 8.5**: скачать/распаковать справку из дистрибутива платформы 8.5
      в папку `1c-help/` (или настроить сервер на онлайн-источник).
- [ ] **Docker Desktop** (для контейнерных серверов) или Node.js 20+
      (для бинарных/npm-серверов).
- [ ] **Cursor** с Claude (Opus/Sonnet последней версии).

Структура проекта пилота:

```
agent-academy-1c-pilot/
├── .cursor/
│   └── mcp.json              ← конфигурация MCP-серверов
├── .cursorrules              ← правила для ИИ (раздел 4)
├── 1c-src/                   ← выгрузка конфигурации в XML
├── 1c-help/                  ← справка платформы 8.5
├── api-contract.yaml         ← контракт HTTP-сервисов (уже есть)
├── tasks/                    ← задачи пилота (md-файлы)
└── output/                   ← сгенерированные модули .bsl
```

## 2. Какие MCP-серверы ставить (минимальный набор)

Отправная точка — каталог: **github.com/Untru/1c-mcp** (curated list всей
экосистемы). Выбирай живые проекты (свежие коммиты). Минимальный контур
из четырёх ролей:

| Роль | Что даёт ИИ | Кандидаты (сверить README) |
|---|---|---|
| **Метаданные конфигурации** | Видит ваши справочники, документы, регистры, реквизиты, модули | mcp-1c (feenlace, один бинарник), 1c_mcp (vladimir-kharin, расширение конфигурации), OneRPA metadata |
| **Справка платформы** | Знает API именно вашей версии (8.5!) | OneRPA docsearch (указать справку 8.5) |
| **Проверка синтаксиса / качество** | Проверяет сгенерированный BSL до того, как ты его вставишь | mcp-bsl-lsp-bridge (BSL LS, 100+ диагностик) |
| **Выполнение в dev-базе** (опционально, этап 2) | Может запустить запрос/код и увидеть результат | Конструктор MCP OneRPA (только dev-база!) |

Начни с первых трёх. Четвёртый добавляй, когда контур заработает.

## 3. Конфигурация Cursor: `.cursor/mcp.json`

Cursor читает MCP-серверы из файла `.cursor/mcp.json` в корне проекта
(или глобально: Settings → MCP). Шаблон (конкретные команды запуска —
из README выбранных серверов, ниже — структура):

```json
{
  "mcpServers": {
    "1c-metadata": {
      "command": "path/to/mcp-1c",
      "args": ["--src", "./1c-src"],
      "description": "Метаданные конфигурации Agent Academy"
    },
    "1c-docs": {
      "command": "docker",
      "args": ["run", "-i", "--rm",
               "-v", "./1c-help:/help",
               "onerpa/docsearch:latest"],
      "description": "Справка платформы 8.5"
    },
    "bsl-check": {
      "command": "path/to/mcp-bsl-lsp-bridge",
      "args": ["--workspace", "./output"],
      "description": "Проверка BSL-кода (BSL Language Server)"
    }
  }
}
```

Проверка: перезапусти Cursor → Settings → MCP → все серверы зелёные.
В чате спроси: «Какие MCP-инструменты тебе доступны?» — Claude должен
перечислить инструменты серверов.

## 4. Дополнение к `.cursorrules` (раздел про 1С 8.5)

Добавь в `.cursorrules` проекта пилота:

```
# Agent Academy — пилот 1С 8.5

## ПЛАТФОРМА

- Целевая платформа: 1С:Предприятие 8.5 (НЕ 8.3)
- Перед использованием любого метода платформы — проверяй его наличие
  и сигнатуру через MCP-инструмент справки (1c-docs)
- Не предлагай API, устаревшие или изменённые в 8.5
- Учитывай новый интерфейс 8.5: оконная система на диалоговых окнах,
  карточки, светлая/тёмная темы, векторные иконки
- При адаптации форм сохраняй совместимость: конфигурация должна
  запускаться и в режиме «Такси» (гибридный переход)

## ОБЯЗАТЕЛЬНЫЙ ЦИКЛ ГЕНЕРАЦИИ КОДА

Для каждой задачи строго по шагам:
1. Прочитай метаданные затронутых объектов через 1c-metadata
   (не выдумывай имена реквизитов — бери реальные)
2. Проверь используемые методы платформы через 1c-docs (версия 8.5)
3. Напиши код в output/<имя-модуля>.bsl
4. Прогони через bsl-check, исправь все замечания уровня Error и Warning
5. Только после этого показывай мне результат + список проверок

## СТИЛЬ КОДА 1С

- Русские ключевые слова (Если, Тогда, КонецЕсли)
- Попытка/Исключение для всех HTTP-вызовов и работы с внешними ресурсами
- HTTP-сервисы возвращают JSON: {success, data, error} по api-contract.yaml
- Даты в ISO 8601
- Имена процедур: глагол + существительное (ПолучитьСписокДоговоров)
- Комментарий-шапка у каждой экспортной процедуры: назначение, параметры,
  возвращаемое значение

## ЧЕГО НЕ ДЕЛАТЬ

- Не генерировать код без чтения метаданных (галлюцинации имён реквизитов)
- Не использовать методы, не найденные в справке 8.5
- Не трогать модули вне задачи
- Не предлагать изменения структуры метаданных без явного запроса
- Не подключаться к продакшн-базе ни при каких условиях
```

## 5. Рабочий цикл и шаблоны промптов

### Промпт-проверка контура (первый запуск)

```
Проверка MCP-контура. Сделай по шагам:
1. Через 1c-metadata: выведи список документов конфигурации,
   содержащих в имени "Договор", с их основными реквизитами.
2. Через 1c-docs: найди описание метода ЗаписатьJSON для платформы 8.5
   и процитируй сигнатуру.
3. Через bsl-check: проверь файл output/test.bsl (создай в нём
   процедуру с намеренной ошибкой и покажи, что проверка её ловит).
Отчитайся по каждому шагу: работает / не работает / что вернул инструмент.
```

Если все три шага прошли — контур готов.

### Шаблон: HTTP-сервис по контракту

```
Задача: HTTP-сервис GET /policies по @api-contract.yaml (operationId getPolicies).

1. Через 1c-metadata изучи документ/регистр, где хранятся договоры агента,
   и справочник агентов. Выпиши реальные имена реквизитов.
2. Спроектируй запрос: фильтры status/type/search/dateFrom/dateTo,
   пагинация page/pageSize, сортировка.
3. Проверь через 1c-docs методы работы с HTTP-сервисами и JSON в 8.5.
4. Напиши модуль в output/http_policies.bsl:
   - формат ответа {success, data, error, meta} строго по контракту
   - обработка ошибок, таймауты
5. Прогони bsl-check, исправь замечания.
6. Покажи код + краткое описание: какие объекты читает, какие индексы
   желательны, что протестировать вручную.
```

### Шаблон: адаптация формы под интерфейс 8.5

```
Задача: адаптировать форму документа [ИмяДокумента] под новый интерфейс 8.5.

1. Через 1c-metadata прочитай текущую структуру формы
   (1c-src/.../Forms/...).
2. Через 1c-docs найди рекомендации 8.5 по: диалоговым окнам, карточкам
   групп, размещению команд рядом с местом действия.
3. Предложи план адаптации СПИСКОМ (не меняй файлы):
   что сгруппировать в карточки, какие команды перенести, что упростить
   до одного клика, что убрать.
4. После моего одобрения — сгенерируй изменённое описание формы и код
   модуля формы в output/, прогони bsl-check.
Учитывай аудиторию: агенты 45+, крупные элементы, минимум скрытых меню.
```

### Шаблон: ревью существующего кода

```
Через 1c-metadata и 1c-src изучи модуль [путь].
Проведи ревью: производительность запросов (запросы в цикле, отсутствие
индексов, избыточные блокировки), обработка ошибок, соответствие 8.5.
Приоритизируй находки: Critical / Major / Minor. Ничего не исправляй,
только отчёт.
```

## 6. Безопасность (жёсткие правила)

1. **Только dev-база.** Серверы с выполнением кода — исключительно на
   обезличенной копии. В mcp.json продакшн-строк подключения быть не должно.
2. **Обезличивание.** В dev-базе заменить ФИО/телефоны/паспорта агентов
   и клиентов на тестовые до подключения ИИ.
3. **Что уходит в облако.** Метаданные и код конфигурации уходят в контекст
   облачной LLM. Данные клиентов — не должны (следствие п.1-2).
   Если политика требует — использовать локальные модели (mcp-1c поддерживает
   Ollama и др.), но качество генерации будет ниже.
4. **Секреты.** Пароли, строки подключения, ключи API страховых — только
   в переменных окружения, никогда в промптах и в выгрузке.
5. **Git.** Папку 1c-src/ можно коммитить (это код), output/ — рабочая,
   .cursor/mcp.json с локальными путями — в .gitignore при необходимости.

## 7. Чек-лист качества (перед принятием кода от ИИ)

- [ ] Имена реквизитов/объектов совпадают с реальной конфигурацией
      (ИИ читал метаданные, а не угадывал)
- [ ] Использованные методы платформы существуют в 8.5 (проверено справкой)
- [ ] bsl-check: ноль Error, Warning осмысленно закрыты
- [ ] Запросы: нет запросов в цикле, есть отборы по индексируемым полям
- [ ] Попытка/Исключение на внешних вызовах
- [ ] HTTP-ответы соответствуют api-contract.yaml
- [ ] Код запускается в dev-базе (ручная проверка / этап 2 — автозапуск)
- [ ] Тимлид 1С посмотрел глазами (первые 2-3 недели — каждый модуль,
      дальше — выборочно)

## 8. Метрика пилота

Чтобы понять, работает ли ставка «ИИ пишет большую часть кода», замеряй
на 5-10 задачах:

| Метрика | Без MCP | С MCP |
|---|---|---|
| Время на задачу (постановка → принятый код) | | |
| Итераций правок до принятия | | |
| Ошибок имён реквизитов (галлюцинации) | | |
| Замечаний bsl-check в первой версии | | |
| Доля кода, написанного ИИ без ручной правки, % | | |

Одну-две задачи сделай в обоих режимах — это даст честное сравнение
для решения о вакансии 1С-мидла и распределении работ со студией.

## 9. Честные флаги (что проверить прежде, чем верить цифре 60-80%)

Добавлено при приёмке playbook в проект — не отменяет ничего выше, а называет риски прямо:

1. **Справка 8.5 = линчпин.** Весь прирост качества держится на шаге «проверь метод в справке 8.5». Если .hbk 8.5 не извлекается / docsearch её не индексирует — шаг тихо деградирует до 8.3, и ИИ снова советует старый API, думая, что проверил. **Смоук-тест до старта:** спросить у 1c-docs свойство/метод, изменённый именно в 8.5, и убедиться, что вернулась 8.5-версия.
2. **bsl-check проверяет ЯЗЫК, а не интерфейс 8.5.** BSL Language Server ловит синтаксис и 100+ диагностик BSL, но не «правильно ли форма адаптирована под новый интерфейс 8.5». Новые свойства управляемых форм он может не знать. Ноль Error ≠ форма соответствует 8.5 — это по-прежнему на тимлида (§7).
3. **Парсер метаданных на XML из 8.5.** До того как доверять контуру — выгрузить ОДНУ форму нового интерфейса и убедиться, что metadata-сервер её распарсил без падения (новые свойства метаданных 8.5 могут ломать парсеры, выросшие на 8.3).
4. **Это не снимает два риска 1С.** Даже идеальный MCP-контур не отвечает на лицензии на масштабе (RAT-2) и 152-ФЗ-хостинг. MCP повышает скорость разработки — но не экономику платформы. Метрика §8 кормит решение о найме/студии, развилку платформы (DECISION) она не закрывает.
5. **RAT playbook'а:** предполагается, что «ИИ пишет большую часть кода 1С, а тимлид проверяет» — рабочая модель. Самый дешёвый способ проверить — §8 на 1-2 реальных задачах в обоих режимах, прежде чем строить на этом план найма.
