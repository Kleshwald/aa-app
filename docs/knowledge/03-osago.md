# 03. Оформление ОСАГО (бизнес-логика)

> Основной источник: `08_module_osago.txt` (модуль «Оформление полиса ОСАГО», ФТ-1…ФТ-45), дополнено `10_skolkovo_report.txt`, `06_ms_segmentation.txt`, `11_service_autoassistant.txt`.
> Контекст (Эванс): **Policy Administration** (котировка → оформление). Оплата — [07](./07-payments.md), сегментация — [08](./08-segmentation.md), пул — [06](./06-autoassistant.md).

## 1. Две карточки: ФЛ и ЮЛ

**[Ф]** Экран оформления содержит **две карточки** с переключателем: физическое лицо и юридическое лицо `[ист: ФТ-31…ФТ-35]`. Выбранный тип сохраняется. Логика разделов ТС / общие данные / водители — общая; отличаются «Страхователь» и «Собственник» и способы оплаты.

> **Прототип:** реализован **только ФЛ**. ЮЛ-карточки нет ни в UI, ни в `api-contract.yaml`. Это крупная дельта — см. [12](./12-gaps-vs-prototype.md).

## 2. Разделы формы ФЛ и обязательные поля

### 2.1 Общие данные `[ист: §5.1.1]`
- **Дата начала** — автозаполняется системой, **разная по СК (от +1 до +4 дней)**, параллельный расчёт `[ФТ-9]`. Дата окончания — авто (обычно +1 год).
- **Цель использования** — по умолчанию «Личная»; выпадающий список `[ФТ-13]`: Личная · Дорожные/специальные ТС · Перевозка опасных грузов · Прокат/аренда · Прочее · Экстренные/коммунальные службы · Регулярные пассажирские перевозки · Такси · Учебная езда. **Влияет на доступные тарифы.**
- **Номер телефона** — вручную, формат `+7 (код) номер` `[ФТ-15]`.
- **Email** — вручную (нужен для отправки полиса, [09](./09-email.md)).

### 2.2 Данные о ТС `[ист: §5.1.2, ФТ-1…ФТ-12]`
- **Автозаполнение по гос.номеру**: ввод ГРЗ → «Найти» → система заполняет **марку, модель, год, мощность (л.с.), VIN, серию/номер СТС, ПТС** из интеграций `[ФТ-1]`. Источники: **Ренессанс, SpectrumData (по VIN), APICloud** `[ФТ-2]`. Если данных нет — поля пустые, вводятся вручную.
- Марка/модель — из справочника «Марки ТС» с автодополнением; если нет — «Модель или марка отсутствуют?» → ручной ввод `[ФТ-8]`.
- **Категория ТС** — выпадающий список. При категории **«F»** — обязательное **ПСМ** (серия/номер + дата выдачи) `[ФТ-10]`.
- **Дополнительные чекбоксы-параметры** `[§5.1.2]`: Техника · ТС с прицепом · Следует к месту регистрации · Зарегистрировано в ИГ · Без номера. «Техника» → обязательные поля ПСМ/ЭПСМ.
- **Без номера** `[ФТ-12]` → поле ГРЗ неактивно.
- **Номер кузова / Номер шасси** `[ФТ-11]` → чекбокс раскрывает обязательные поля.

### 2.3 Данные о страхователе `[ист: §5.1.3, ФТ-3…ФТ-6, ФТ-14]`
- Фамилия, Имя, Отчество (автодополнение ФИО `[ФТ-23]`), Дата рождения.
- Чекбокс **«Без отчества»** → поле отчества неактивно `[ФТ-14]`.
- **Тип документа**: по умолчанию «Паспорт РФ»; альтернатива «Иностранный паспорт» → появляется поле «Страна» `[ФТ-4, ФТ-5, ФТ-6]`.
- Серия, Номер, Дата выдачи.
- **Адрес регистрации** — автодополнение из **DaData**; адреса вне списка DaData не принимаются `[ФТ-27, §5.1.3]`.

### 2.4 Данные о собственнике `[ист: §5.1.4, ФТ-17]`
- Чекбокс **«Собственник является страхователем»** → автозаполнение из страхователя `[ФТ-17]`.
- Иначе — те же поля, что у страхователя (ФИО, ДР, документ, адрес). Адрес собственника используется сегментацией (открытость территории) `[ФТ-40]`.

### 2.5 Данные о водителях `[ист: §5.1.5, ФТ-22, ФТ-36, ФТ-37]`
- **Количество водителей 1–5 или «Без ограничений»** (значение по умолчанию — «Без ограничений») `[ФТ-22]`.
- Тип лица: **Собственник / Страхователь** → автозаполнение; **Иное лицо** → ручной ввод.
- Для «иного лица»: Фамилия, Имя, Отчество, чекбокс «Без отчества», Дата рождения; **ВУ**: тип (обычное/иностранное), серия (обяз.), номер (обяз.), дата выдачи (обяз.), **дата начала стажа (обяз.)** `[ФТ-37]`.
- Иностранное ВУ → номер/серия/страна (обяз.).
- Чекбокс «Указать предыдущее ВУ» → номер предыдущего ВУ (обяз.).
- Чекбокс «Другая фамилия» → поле «другая фамилия».

> **Прототип** покрывает автозаполнение ТС, справочник марок, водителей, маски, «Ассистент, заполни» (см. память `project_taiga_form_pattern`). Полнота полей (ПСМ/ЭПСМ, иностранные документы, предыдущее ВУ) в прототипе частичная — сверять при проектировании V1.

## 3. Карточка ЮЛ (отличия) `[ист: §5.2, ФТ-19…ФТ-21, ФТ-44]`

- **Страхователь/Собственник ЮЛ**: ввод **ИНН** → автозаполнение через **DaData**: полное наименование, тип документа (ОГРН), серия/номер, дата выдачи, **КПП**, юридический адрес `[ФТ-26, §5.2.1]`.
- Тип документа по умолчанию — «Выписка из ЕГРЮЛ»; альтернативы — «Свидетельство о постановке на налоговый учёт» / «Свидетельство о регистрации» (тогда обяз.: Серия/Номер/Дата/КПП/ОГРН) `[ФТ-20, ФТ-21]`.
- Чекбокс «Собственник является страхователем» → автозаполнение `[ФТ-19]`.
- **Способ оплаты ЮЛ**: переключатель **Банковская карта / Счёт на оплату** `[ФТ-44, §5.2.2]`. См. §7.

## 4. Основной сценарий (happy path) `[ист: §6.1]`

```
1. Агент авторизован → страница ОСАГО (пункт «Авто» / в новом фронте — «ОСАГО»)
2. Заполняет форму (ТС, страхователь, собственник, водители, общие)
3. Жмёт «Рассчитать»
   → внутренний СКОРИНГ (чёрные списки, профили)  [08]
   → СЕГМЕНТАЦИЯ: открыта ли территория по адресу собственника  [08]
   → получение КБМ и коэффициентов (ApiCloud) для возможного пула  [06]
   → котировки уходят в отобранные СК (свой набор данных на каждую) [ФТ-41]
   → у каждой СК процесс в 2 ЭТАПА: расчёт + выгрузка договора       [ФТ-28]
   → анализ: зелёный переход / пролонгация / новый бизнес          [ФТ-39]
   → авто-выбор СК ИЛИ показ списка одобренных                     [ФТ-39]
4. Модальное окно «Колесо» (индикатор поиска), ждём ответы СК+РСА   [ФТ-43]
5. Показ тарифов + кросс-продуктов:
   • В СЕГМЕНТЕ → ОСАГО можно без кросс-продукта
   • В ПУЛЕ    → кросс-продукт ОБЯЗАТЕЛЕН, кнопка «Продолжить»       [ФТ-28]
6. Оплата (см. §7). ФЛ — карта; можно «Скопировать ссылку на оплату»
7. Экран «Полис оформлен» → скачать полис + заявление              [ФТ-25]
8. Отправка документов клиенту на email через Dashamail, каждые 10 мин [ФТ-42, 09]
```

**[Ф]** Данные сохраняются, если нажали «Рассчитать/Оформить» или «Сохранить черновик» `[ФТ-16, ФТ-29]`. Черновик позволяет вернуться и дозаполнить.

## 5. Коэффициенты и расчёт премии

**[Ф]** **КБМ** приходит из внешнего источника — **ApiCloud** (для оформления через РСА/пул), не считается локально `[ФТ-38, 11_service_autoassistant.txt §3]`. Остальные коэффициенты «Автопомощника» разрабатывают внутренние специалисты на основе тарифов `[ист: 11_service_autoassistant.txt §3]`.

**[Ф]** Собственно тариф ОСАГО в сегменте возвращает **СК по котировке** — двухэтапно (расчёт → выгрузка) `[ФТ-28]`. Метод расчёта различается по СК (см. [11 §Интеграции](./11-legacy-architecture.md)).

**[Г] Полная формула ОСАГО** (отраслевая, Указание ЦБ): `Премия = ТБ × КТ × КБМ × КВС × КМ × КО` (+ КС/КП/КН). В документах легаси формула **не приведена** — расчёт делегирован СК и РСА. Для нового фронта это важно: **фронт не считает премию**, он показывает то, что вернули СК/пул. См. [13, Q2](./13-open-questions.md).

## 6. Отбор СК и авто-выбор `[ист: ФТ-39…ФТ-41]`

- **[Ф]** Список СК для запроса определяется по **открытым категориям, регионам и настройкам агента** (профиль агента, [08](./08-segmentation.md)) `[ФТ-41]`.
- **[Ф]** Возможность страхования территории проверяется по адресу собственника `[ФТ-40]`.
- **[Ф]** Система либо **сама выбирает СК**, либо предлагает агенту **список одобренных** `[ФТ-39]`.
- **[Ф]** Настройка профиля может «отправить в несколько СК, показать одну» `[ист: 06_ms_segmentation.txt §4]` — важный нюанс UX: экран показывает не все ответы.

## 7. Оплата `[ист: §5.2.2, ФТ-24, ФТ-44, ФТ-45; 07]`

| Тип клиента | Способы |
|-------------|---------|
| **ФЛ** | Только банковская карта (эквайринг). Способ выставляется автоматически при отправке в СК `[ФТ-45]` |
| **ЮЛ** | Банковская карта **или** счёт на оплату `[ФТ-24, ФТ-44]` |

**[Ф]** Особенности по СК:
- **Ренессанс**: оплата картой — эквайринг Ренессанса **либо наш**; счёт для ОСАГО формируется через API Ренессанса, для кросс-продукта — через наш сервис; после оплаты по счёту — приложить чеки и «Оформить» `[§5.2.2]`.
- **Согласие**: **всегда эквайринг Согласия**; кросс-продукты — **всегда наш эквайринг**; **оплаты по счёту нет** `[§5.2.2]`.
- Кросс-продукты по ЮЛ — всегда наш эквайринг.
- Карты: Visa, Мир, Mastercard, Maestro `[§6.1]`.
- Оплата по счёту (ЮЛ): скачать счёт → оплатить через банк/бухгалтерию → приложить чеки → «Оформить» в котировке.

## 8. Статусы (котировка / полис) `[ист: 10_skolkovo_report.txt §3.9]`

**[Ф]** Статусы **котировки**: **Черновик** (расчёт был, но не оплачен / нажали «Сохранить в черновик») · **Оформлена** · **Оформляется** (в процессе).
Полный ЖЦ котировки: приём заявки → внутренний скоринг → сегментация → решение о выводе тарифа → вывод на экран → оформление → **начисление КВ**.

> **Прототип** сводит статусы к двум: `active` («Оформлен») и `pending` («Черновик») — «Оформляется»/processing не используется. Контракт при этом объявляет `active/expired/cancelled/pending/processing`. См. [12](./12-gaps-vs-prototype.md).

## 9. Документы `[ист: ФТ-25, ФТ-42]`

- Скачать можно: **страховой полис, заявление на страхование, кросс-продукт** — если статус «Оформлен» `[ФТ-25]`.
- Отправка клиенту — на email через **Dashamail**, PDF, циклично **каждые 10 минут** `[ФТ-42, 09]`.

## 10. Исключения и граничные случаи (Коберн) — что «если пойдёт не так»

Документы легаси описывают happy path; ниже — риски, которые **нужно спроектировать** в V1. Отмечено, есть ли решение в источнике.

| Ситуация | Что в легаси | Риск для нового фронта (3G/старый ноут) |
|----------|--------------|------------------------------------------|
| **Обрыв связи на «Колесе»** (ждём СК/РСА) | Не описано | Долгий синхронный запрос к 7 С(×2 этапа). На 3G — таймаут. Нужны: таймаут per-СК, `failedCompanies` (в контракте есть!), частичный показ, retry |
| **Двойное нажатие «Оплатить»** | Не описано | **P0. Идемпотентность.** Списание без полиса. Нужен idempotency-key на оформление/оплату — см. [07](./07-payments.md) |
| **Деньги списались — полис не выпущен** | Косвенно: «подтверждение платежа» у СК, ручной `confirmPayment` (Ренессанс) | Нужна сверка платёж↔полис; статус «Оформляется» как раз про это |
| **СК не ответила / отвалилась** | `failedCompanies` в контракте; «если СК нужно больше времени — счёт появится в комментариях котировки» `[§6.2]` | Показать частичный результат, не блокировать весь экран |
| **Нет одобрения на сегмент** | Переход в **пул/Автопомощник** с обязательным кросс `[06]` | Отдельная ветка UX (обязательный доп) |
| **Не прошёл скоринг / чёрный список** | Котировка не отправляется в СК `[08]` | Нужен понятный агенту месседж без «страшных» формулировок |
| **F5 на свежем договоре** | — (в 1С — серверное хранение) | В прототипе договор in-memory → теряется. В V1 (1С) — не проблема, но UX-состояние формы стоит сохранять в черновик |
| **Устаревший КБМ** | КБМ тянется из ApiCloud/РСА на момент расчёта | При пере-котировке КБМ может измениться → цена «прыгает». Предупреждать |
| **Оплата по счёту ЮЛ не подтверждена** | Приложить чеки вручную → «Оформить» | Ручной шаг, полу-асинхронный; статус «Оформляется» |

**Идемпотентность (Хоп):** операции **«Оформить» (`/calculations/{id}/proceed`) и «Оплатить» — write-операции с деньгами**. В V1 обязателен идемпотентный ключ и защита от повторной отправки на клиенте (disable + токен запроса). В контракте сейчас этого нет — [13, Q3](./13-open-questions.md).
