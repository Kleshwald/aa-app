# 12. Дельта: легаси ↔ Angular-прототип

> Сверка бизнес-логики легаси (файлы 01–11) с текущим прототипом: `api-contract.yaml`, `src/app/core/mock/**`, `src/app/core/services/**`, `src/app/core/models/**`, `src/app/features/**`.
> Принцип **«мок ≠ контракт»**: отдельно помечаю, что реализовано в моке, но отсутствует в `api-contract.yaml` (источник правды для 1С-команды).
> Приоритеты: **P0** — ломает флоу/деньги/данные · **P1** — важная бизнес-логика, без неё V1 неполон · **P2** — полировка/вторичное.

## B. «Мок ≠ контракт»: реализовано в моке, но отсутствует в `api-contract.yaml`

Это долг синхронизации — 1С-команда по контракту эти endpoints **не увидит**.

| Endpoint (мок/handler) | В контракте? | Приоритет | Замечание |
|------------------------|--------------|-----------|-----------|
| `GET /prolongations`, `GET /prolongations/stats` | **Нет** | P1 | `prolongations.handler.ts`, используется страницей пролонгации |
| `POST /nsis-search` | **Нет** | P1 | Поиск НСИС; в контракте нет вовсе (и термин РСА vs НСИС) |
| `GET/POST /processes*` (заявки change/cancel/loss, awaiting, comments, attachments) | **Нет** | **P1** | Целый контекст процессов вне контракта |
| `POST /policies` (создание договора после оплаты) | **Нет** (есть только `GET /policies`) | **P0/P1** | Прототип создаёт полис через POST /policies; контракт предполагает `/calculations/{id}/proceed` → Policy. **Развилка в модели оформления** — надо привести к одному |
| `GET /agents/team` | **Нет** | P2 | «Команда» (сотрудники/субагенты) |
| `GET /finance*` | **Нет** | P2 | Финансы |
| Health/НС расчёт и оформление | **Нет** | P1 | `calculations/osago` есть, аналога для НС/Антиклещ нет |
| `POST /policies/{id}/cancel`, `/prolong` | **Да** | — | Есть в контракте (но cancel без расчёта возврата) |

## E. Сводка приоритетов (что чинить/решать в первую очередь для V1)

**P0 (деньги/данные/флоу):**
- A1 идемпотентность оплаты и оформления; согласовать модель «оформление → полис» (проблема POST /policies vs proceed, B).

**P1 (несущая бизнес-логика):**
- A2 сегмент/пул + обязательный кросс; A3 ЮЛ (решить скоуп); A4 кросс-продукты в контракте; A5 статусные модели процессов; A6 «Оформляется»; A13 UX отказа скоринга; A14 полнота полей расчёта; B (prolongations/processes/nsis-search/health в контракт).

**P2 (полировка/вторичное):**
- A8 расчёт возврата; A9 финансы; A10 аналитика; A11 ипотека; C-расхождения enum/модели (привести контракт↔мок↔легаси к согласию).

## F. Рекомендация аналитика
Прежде чем расширять UI, **синхронизировать `api-contract.yaml` с реальными потребностями** (раздел B) — иначе 1С-команда получит контракт, не покрывающий половину экранов прототипа (процессы, пролонгация, НСИС, здоровье, создание полиса). Это API-First принцип самого проекта (`ARCHITECTURE.md`).
