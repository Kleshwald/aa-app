# 08. Сегментация и скоринг

> Источники: `06_ms_segmentation.txt` (микросервис «Сегментация»), `10_skolkovo_report.txt` (§4.5 скоринг/сегментация, §3.9.2 ЖЦ котировки, §5 управление профилями/чёрные списки).
> Контекст: сквозной сервис перед **Policy Administration** (решает, отправлять ли котировку в СК и какую цену показать). Тесно связан с [06-autoassistant](./06-autoassistant.md).

## 1. Зачем

**[Ф]** Сегментация делит клиентскую базу на группы по характеристикам, чтобы соответствовать внутренним правилам AA и правилам СК, и формировать «качественный портфель» для партнёров `[ист: §1, §6]`. Это **фильтр качества и допуска**, а не маркетинговая рассылка.

## 2. Данные для сегментации `[ист: §2.1]`

**[Ф]** Используется всё из договора страхователя; ключевое — **регион/район собственника (адрес регистрации)**. Плюс параметры:
- Категория ТС (легковой/грузовой), Марка, Модель, VIN, Год выпуска.
- **Списки запрещённых ТС** (не подлежат страхованию).
- Возраст собственника, Масса ТС.
- **КБМ** (из ApiCloud).
- Цель использования.

## 3. Процесс сегментации `[ист: §2.2]`

```
1. Открытость территории:
   • открыта ли территория страхования по адресу регистрации собственника
   • можно ли отправить котировку в СК по правилам
   → если оба да → данные уходят в СК
2. Расчёт с разными датами: +1..+4 дня начала в разных СК
3. Выгрузка договоров: по успешным предложениям (процесс в 2 этапа)
4. Анализ данных: зелёный переход / пролонгация / новый бизнес
5. Выбор СК: авто ИЛИ список одобренных агенту
```
`[ист: §2.2.1–2.2.5]`

## 4. Внутренний скоринг (перед отправкой в СК) `[ист: 10_skolkovo_report.txt §3.9.2]`

**[Ф]** Полный ЖЦ котировки проходит внутренний скоринг:
1. **Проверка данных** — в т.ч. на наличие в **чёрных списках**.
2. **Сегментация** — открыта ли территория для агента по собственнику; открыты ли территории/сегменты у СК.
3. Бизнес-правила допуска:
   - **Профиль запрета продаж** — заблокированные агенты не продают.
   - **Профиль сегментации (СК, территория, ТС)** — котировки вне настроек СК отсекаются.
   - **Группа сегментации** — заблокированные для продаж территории.
4. Если клиент/ТС **не прошли чёрные списки — котировка в СК не отправляется** `[§3.9.2]`.
5. Решение: **выводить тариф на экран или нет** → вывод → оформление → **начисление КВ**.

## 5. Чёрные списки `[ист: 10_skolkovo_report.txt §5.4]`

**[Ф]** Клиент/ТС попадает в чёрный список по правилам:
- Убыточность (выплаты >> премии).
- Быстрые убытки (крупный убыток вскоре после заключения).
- Нецелевая территория.
- Крупные убытки (свыше лимита).
- Комбинация факторов.
- Мошенничество.

**[Ф]** Занесение → отказ в заключении/продлении, доп. контроль. Данные об убытках получают из ИС СК; можно запрашивать первичные документы по убыткам `[§5.4]`.

## 6. Методы `[ист: §2.3]`

**[Ф]** СКД (система компоновки данных 1С) для запросов, запросы к БД, **API-Cloud для получения КБМ из СК**.

**[Ф]** Обновление сегментов — редко, по инициативе бизнеса + техкоманда `[§2.4]`. Настройка: часть — бизнес, часть — техкоманда `[§3]`.

## 7. Профили агентов и «что показать на экране» `[ист: §4, 10_skolkovo_report.txt §5.2, §5.3]`

**[Ф]** Через **профиль агента** админ настраивает:
- Доступные территории страхования.
- Доступные СК и **последовательность их вывода на экран**.
- Пул/сегмент агентов.
- Параметры сегментации AA.
- **Кросс-продукты по каждой СК** (обязательные/необязательные, цена ползунком).
- Флаги: запрет продаж / запрет продаж в Ренессанс / запрет страхования ТС без VIN.

**[Ф] Критичный нюанс UX** `[ист: §4]`: можно **отправить расчёт в несколько СК, но показать только одну** — зависит от профиля агента и профиля СК. → Экран котировок показывает **не все ответы**, а отфильтрованный/упорядоченный профилем набор.

## 8. ML / NLP `[ист: 03_tech_architecture.txt §1.2, 10_skolkovo_report.txt]`

**[Ф]** Заявлены ML и NLP как основа «персонализированного подхода», скоринга и оценки мошенничества `[ист: 01/03_...]`. **[Г]** Конкретные модели/фичи/метрики в документах **не описаны** — это уровень деклараций (вероятно, для реестра/гранта). Сторонние сервисы данных: **SpectrumData, ApiCloud** `[§4]`.

**Вывод:** для V1-фронта ML/NLP — **чёрный ящик на стороне 1С/сервисов**. Фронт получает уже готовое решение (одобрено/нет, список СК, цена). Не проектировать ML в прототипе.

## 9. Что из этого видит агент (и что должно попасть в новый фронт)

| Внутренняя логика | Проявление для агента |
|-------------------|-----------------------|
| Открытость территории | Есть/нет предложений; уход в пул |
| Чёрные списки / скоринг | «Не прошли скоринг» (фильтр в пролонгации), отказ без пугающих деталей |
| Профиль агента (порядок/фильтр СК) | Какие СК и в каком порядке видны в котировках |
| Обязательные кросс по профилю | Обязательный доп в пуле/по СК |
| Сегмент vs пул | С кросс-продуктом или без; разный КВ |

> **Прототип** сегментацию/скоринг/чёрные списки **не моделирует** вовсе. Экран котировок показывает фикс-набор СК без оси «сегмент/пул». Это одна из главных содержательных дельт — см. [12](./12-gaps-vs-prototype.md), т.к. от неё зависит корректность цен и КВ.

## 10. Исключения (Коберн)
- **Территория закрыта** → сразу пул/Автопомощник или отказ; не показывать «пустой экран без объяснения».
- **Все СК отфильтрованы профилем** → агент видит 0 предложений при технически успешном расчёте — нужен понятный месседж.
- **КБМ не пришёл (ApiCloud недоступен)** → расчёт невозможен/деградирует; ретрай.
