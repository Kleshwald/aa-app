# 07. Оплаты (Billing-контекст)

> Источники: `04_ms_payments.txt` (микросервис «Оплата»), `10_skolkovo_report.txt` (интеграции эквайрингов, §4.6), сверка модулей ОСАГО/Здоровье.
> Контекст (Эванс): **Billing** — приём оплаты, статусы платежа, возвраты. **Не смешивать** с Policy Administration.

## 1. Эквайеры

**[Ф]** Используются **два эквайринга**: **Best2Pay** и **ЮКасса** `[ист: §Введение]`. Плюс — **эквайринги самих СК** (Ренессанс, Согласие и др.) для части оплат.

Кто чем платится (сводка из [03](./03-osago.md), [04](./04-health.md)):

| Что оплачивается | Эквайринг |
|------------------|-----------|
| НС универсальный / НС спорт | **Best2Pay** `[07_module_health.txt ФТ-12]` |
| Антиклещ | Эквайринг СК (Согласие, Югория) `[ФТ-13]` |
| ОСАГО Ренессанс | Эквайринг Ренессанса **или наш** `[08_module_osago.txt §5.2.2]` |
| ОСАГО Согласие | **Всегда** эквайринг Согласия `[§5.2.2]` |
| Кросс-продукты (ЮЛ и по Согласию) | **Всегда наш эквайринг** `[§5.2.2]` |
| ЮКасса | Упоминается как второй эквайер `[04_ms_payments.txt]`; в отчёте — редирект на ЮКасса для оплаты картой `[10_skolkovo §...]` |

> **Вывод для архитектуры:** «оплата» — **не один провайдер**, а маршрутизатор: по СК/продукту выбирается эквайер. Это влияет на статусы, коллбэки и сверку.

## 2. Платёжные методы `[ист: §Общая информация]`

**[Ф]** Поддерживаются карты: **Visa, MasterCard, Мир, Maestro** `[04_ms_payments.txt; 08_module_osago.txt §6.1]`.
**Не используются:** P2P (перевод карта-карту), **оплата QR-кодом СБП** `[04_ms_payments.txt]`.

## 3. API Best2Pay `[ист: §Методы API]`

**[Ф]** Методы:
| Операция | Метод | URL |
|----------|-------|-----|
| Регистрация заказа | POST | `/webapi/Register` |
| Получение статуса заказа | POST | `/webapi/Order` |
| Ссылка на страницу оплаты (обычная) | GET | `/webapi/Purchase?<строка запроса>` |
| Ссылка на оплату (безопасная сделка) | GET | `/webapi/SafeDepositDebit?<строка запроса>` |

**[Ф]** В каждом методе передаётся **`signature`** (цифровая подпись по алгоритму на основе полей заказа) `[ист: §Методы API]`. **«Безопасная сделка»** (`SafeDepositDebit`) — двухфазный платёж (холдирование), включается параметром.

**[Ф]** ЮКасса — интеграция через **виджет** (`yookassa.ru/developers/.../widget`) `[ист: ссылка]`.

## 4. Флоу оплаты (обобщённо)

```
Оформление (после выбора тарифа)
  → регистрация заказа у эквайера (Register / виджет)
  → получение ссылки на оплату (Purchase / SafeDepositDebit) ИЛИ редирект (ЮКасса/СК)
  → клиент платит картой (номер, срок, CVC) + согласие с офертой
  → подтверждение платежа:
       • автоматически (коллбэк эквайера), ИЛИ
       • ручное confirmPayment у СК, если платили сторонним эквайером (Ренессанс)  [11 §Интеграции]
  → статус заказа (Order) → выпуск/оформление полиса
  → печатные формы от СК → документы клиенту (Dashamail, каждые 10 мин)  [09]
```

**[Ф]** «Скопировать ссылку на оплату» — агент может отправить клиенту ссылку `[08_module_osago.txt §6.1]`.

## 5. Статусы платежа

**[Г]** В документах явная модель статусов платежа **не описана** — есть только методы `Register`/`Order`/`confirmPayment`. Реконструкция (отраслевая + методы Best2Pay):
```
NEW (зарегистрирован) → AUTHORIZED (для безопасной сделки, холд)
      → PAID / COMPLETED (списан)
      → DECLINED / FAILED (отказ)
      → REFUNDED (возврат)
      → EXPIRED (ссылка протухла)
```
→ **[П]** Точную статусную модель эквайринга подтвердить (Q3). Для фронта V1 важно, что оплата **асинхронна** (коллбэк) и полис появляется **после** подтверждения.

## 6. Возвраты `[ист: 12_processes_1_0.txt — расторжение]`

**[Ф]** Возврат части премии считается при **расторжении** (не в микросервисе оплаты, а в процессах, [10](./10-processes.md)):
```
Сумма к возврату = (Премия − 0.23 × Премия) / дней действия полиса × дней остатка
```
`[ист: 12_processes_1_0.txt, Расторжение ФТ-4]`. То есть 23% премии удерживается (РВД + отчисления), остаток возвращается пропорционально неистёкшему сроку.

**[Г]/[П]** Возврат по **выплате убытка** — отдельный денежный поток (не «возврат», а выплата на счёт клиента), см. [10](./10-processes.md). Механику возврата эквайрингом (на карту / реквизиты) документы не детализируют — Q3.

## 7. Исключения и НФТ (Коберн + Хоп) — критично для денег

| Ситуация | Что делать в V1 |
|----------|-----------------|
| **P0. Двойное нажатие «Оплатить»** | **Идемпотентность обязательна**: idempotency-key на регистрацию заказа; на клиенте — disable кнопки + токен. Best2Pay `Register` с одинаковым orderId не должен создавать второй платёж |
| **P0. Деньги списаны, полис не выпущен** | Сверка `Order`(эквайер) ↔ статус полиса(СК). Полис в «Оформляется» до подтверждения. Ретрай `confirmPayment` |
| **Обрыв связи после «Оплатить» (3G)** | Не создавать второй заказ при повторе; по возврату на экран — сначала запросить статус (`Order`), потом решать |
| **Коллбэк эквайера не пришёл** | Поллинг статуса `Order`; таймаут; уведомление агенту «оплата проверяется» |
| **Оплата по счёту ЮЛ** | Полу-ручной: клиент платит по счёту → агент прикладывает чеки → «Оформить». Статус «Оформляется» до подтверждения |
| **Согласие: объединение счетов ОСАГО + МиниКАСКО** | Отдельная GraphQL-операция у Согласия `[11 §Интеграции]` — один платёж на два продукта. Учесть в маршрутизаторе оплат |
| **Аудит** | Все финоперации логировать (152-ФЗ, ЦБ). На стороне 1С (as-is). Фронт не логирует ПДн/карты |

## 8. НФТ под профиль (3G / старый ноут)
- Оплата — **редирект/виджет эквайера**, тяжёлый сторонний JS. На 3G — риск долгой загрузки. Показывать понятный лоадер, не давать жать повторно.
- Карточные данные фронт **не хранит и не логирует** (PCI DSS ответственность у эквайера). Форма карты — на стороне эквайера (виджет/редирект), не наша.
