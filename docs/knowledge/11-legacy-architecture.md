# 11. Легаси-архитектура (AS-IS) — справка, НЕ цель

> ⚠️ **Это описание ДЕЙСТВУЮЩЕЙ системы на 1С (as-is).** Новая система строится с **другой** архитектурой (Angular-фронт напрямую к HTTP-сервисам 1С в V1, `ARCHITECTURE.md`). Здесь фиксируем как-есть, чтобы понимать **источник данных, интеграции и НФТ**, а не чтобы копировать. UX 1С — анти-референс.
> Источники: `03_tech_architecture.txt`, `01_func_characteristics.txt`, `10_skolkovo_report.txt §4`.

## 1. Общая конструкция `[ист: 03_tech_architecture.txt §2]`

**[Ф]** Трёхуровневая клиент-серверная архитектура на 1С:Предприятие 8.3:
- **Уровень 1 — клиент:** веб-клиент (HTML5, WebSocket), тонкий клиент 1С (TCP/IP), толстый клиент (администрирование).
- **Уровень 2 — сервер приложений:** кластер 1С (менеджер `rmngr` + рабочие процессы `rphost`), веб-сервер **Microsoft IIS** (HTTPS, SSL termination, маршрутизация на 1С).
- **Уровень 3 — СУБД:** **Microsoft SQL Server 2019+** (бизнес-данные, метаданные, TDE-шифрование).

**[Ф]** Всё размещено в **ЦОД на территории РФ** на виртуальных серверах Windows Server 2019+ `[§4]`. Объектное хранилище — **MinIO** (S3-совместимое) `[01_func_characteristics.txt]`.

## 3. Интеграции (карта внешних систем) `[ист: 10_skolkovo_report.txt §4, 03_tech_architecture.txt §6]`

**Это самая ценная часть для нового фронта** — источники данных и точки отказа.

### 3.1 Страховые компании (котировка/оформление/пролонгация)
Двухэтапно у всех (расчёт → выгрузка), но **API у каждой СК своё**:

| СК | Протокол | Формат | Авторизация | Особенности |
|----|----------|--------|-------------|-------------|
| **Ренессанс** | REST | JSON | OAuth 2.0 Bearer | `/calculate`, `/import`, `/getAccountStatus`, `/confirmPayment` (ручное подтв. при стороннем эквайринге), `/printDocument`, `/dictionaries`. Синхр. и асинхр. методы |
| **Югория** | REST | JSON | API Key | `create` (проект/расчёт), `policy` (подтв./инфо/печать) |
| **Евроинс** | REST | **XML** | Basic | `USER_AgrCalcOsagoExportPlus`, `USER_SavePolicyProject`, `USER_GetPaymentPageOSAGO`, `USER_CheckPayment`, `USER_ActivateOsago`, `USER_GetEpolicyLink` |
| **Ингосстрах** | REST | **XML** | API Key | `CreateAgreement`, `UpdateAgreement`, `GetAgreement`, `CreateBill`, `CreateOnlineBill`, `FixPayBill`, `GetPolicyDocuments` |
| **Согласие** | REST **+ GraphQL** | JSON | API Key | `/rsaproxy/api/osago/v1/kbm` (КБМ), `/CCM/CCMService` (расчёт), `/online/api/eosago` (импорт), **GraphQL «объединение счетов»** ОСАГО+МиниКАСКО |
| **Зетта** | REST | JSON | Basic | `Quote.cmd`, `GetQuoteStatus.cmd`, `Accept.cmd` (акцепт котировки) |
| СОГАЗ, Росгосстрах | — | — | — | В партнёрах названы, детальных методов в документе нет `[03 §6.1]` |

**Общие этапы интеграции с СК** `[10_skolkovo §4.6]`: предрасчёт → импорт данных в AA → оплата (ссылка на оплату / редирект) → подтверждение оплаты → статус котировки → печатные формы. **Методы каждого этапа различаются по СК.**

## 4. Безопасность `[ист: 03_tech_architecture.txt §7, 01_func_characteristics.txt]`

**[Ф]**
- **2FA** при первичной регистрации (Email + телефон); парольная политика + OTP; восстановление пароля.
- **RBAC** на уровне метаданных и записей 1С; **RLS** (Record Level Security).
- **TLS 1.2+ / HTTPS**; SSL-терминация на IIS; token-based auth для REST-интеграций.
- **TDE** (шифрование БД MS SQL) + шифрование бэкапов.
- **Журнал регистрации 1С** — аудит всех действий (важно для финопераций, ЦБ, 152-ФЗ).
- Сетевая сегментация: **DMZ (веб) / прикладная зона (1С) / зона данных (СУБД)**; firewall; IP-ограничение для админ-интерфейсов.
- **Один телефон = один ЛК**.

## 5. НФТ, обеспечиваемые архитектурой `[ист: §8, §9]`

| Характеристика | Как обеспечено (as-is) |
|----------------|------------------------|
| Масштабируемость | Горизонтальная (доб. серверов/`rphost` в кластер) + вертикальная |
| Надёжность | Кластер 1С с авто-перезапуском `rphost`; MS SQL AlwaysOn; ежедневные бэкапы |
| Доступность | Целевая **99.5%**; SaaS, браузер |
| Производительность | Кэш на 1С, оптимизация SQL, разделение серверов, балансировка |
| Бэкап | Ежедневно полный, окно 22:00–00:00, глубина **30 дней** |

**Требования к серверам** `[§4.4]`: сервер приложений 8 ядер / 16 ГБ / 200 ГБ SSD / 1 Гбит; СУБД 8 ядер / 32 ГБ / 500 ГБ SSD / 1 Гбит.

## 6. Что из этого важно новому фронту (перенос знаний, не архитектуры)

1. **Источник данных V1 — HTTP-сервисы 1С** (REST, JSON, JWT). Легаси-интеграции со СК/РСА/DaData/эквайрингами **остаются в 1С** — фронт их не трогает напрямую (`ARCHITECTURE.md`).
2. **Разнородность СК** (JSON/XML, OAuth/Basic/ApiKey, свои эквайринги, 2 этапа) → долгие/частично-падающие расчёты. Контракт фронта уже это учитывает полем `failedCompanies`. Держать таймауты/деградацию.
3. **Аудит финансов и ПДн — на стороне 1С.** Фронт: не логировать ПДн/карты, маскировать номера документов.
4. **152-ФЗ**: всё в РФ. Влияет на выбор чат-бэкенда и любых новых внешних сервисов.
5. **UX 1С не наследуем** (лишние скроллы, подрезанные формы, «непонятно новым агентам» — прямые боли из PROJECT_BRIEF).
