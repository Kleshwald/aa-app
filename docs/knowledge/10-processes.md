# 10. Процессы управления договорами

> Источник: `12_processes_1_0.txt` (процессы 1.0). Это **источник правды по статусным моделям**.
> Контекст (Эванс): **Endorsement** (внесение изменений) и **Cancellation** — Policy Administration; **Claims** (урегулирование убытков) — отдельный контекст. Держать раздельно, не сваливать в «страницу договора».

## 0. Общая рамка `[ист: §1, §1.1]`

**[Ф]** Из карточки договора («Мои клиенты» → договор → подраздел **«Процессы»**) агент инициирует **три процесса**:
1. **Внесение изменений (ВИ)** в полис.
2. **Расторжение** полиса.
3. **Урегулирование убытка (УУ)**.

**[Ф]** Заявки автоматически попадают в раздел **«Мои заявки»**, где их обрабатывает **техподдержка** `[ФТ-4]`. По **Ренессансу** заявки на **изменение** проходят **автоматическую обработку** (интеграция) `[§1, ВИ-ФТ-3]`.

**[Ф]** Уведомления: при создании — № заявки на email `[ФТ-2]`; при смене статуса/комментарии — уведомление агенту `[ФТ-7]`; ошибка отправки → сообщение «попробовать снова» `[ФТ-3]`. Общение агент↔поддержка — **внутри платформы** `[ФТ-11]`.

**[Ф]** На «Мои клиенты» к таблице договоров добавлено отображение **статуса и вида процесса** `[ФТ-10]`.

> **Прототип** реализует ровно эти три процесса как `ProcessKind = 'change' | 'cancel' | 'loss'` (`process.service.ts`), плюс сквозной сигнал «Ждут ваших действий» (память `project_attention_signal`) и маркер заявки в строке «Мои клиенты» (память `project_process_visibility`). **Но статусные модели прототип сильно упростил** — см. §5 и [12](./12-gaps-vs-prototype.md).

## 1. Внесение изменений (ВИ) `[ист: раздел «Внесение изменений»]`

**Форма заявки:** причина изменения + документы + корректные данные в форме договора `[ВИ-ФТ-1]`.

**[Ф] Причины изменения** `[ВИ-ФТ-3]` (не исчерпывающий список): вписание нового ГРС; замена ВУ; вписание нового водителя.
> Прототип `CHANGE_REASONS` расширяет до 12 кодов: add-driver, replace-license, policy-error, change-owner, replace-plate-sts, unlimited-drivers, with-trailer, policyholder-doc, owner-doc, remove-driver, owner-name, policyholder-name (`process.service.ts`).

**[Ф] Статусная модель ВИ** `[ВИ-ФТ-4]`:
```
Новый → В работе → Ожидаем документы → Ожидаем оплаты → Готово
                                                          → Отказ
```
**Системные статусы** (авто) `[ВИ-ФТ-5]`:
- **Документы загружены** — авто при успешной загрузке агентом.
- **Оплачен** — авто после успешной оплаты договора агентом.

**[Ф] Карточка задачи (поддержка)** `[ВИ-ФТ-7]`: № полиса · Дата · СК · Страхователь · Тип заявки · Причина изменения · Комментарии/действия агента · Заметки ТП · Приложенные файлы · Статусы.
Кнопки: Приложить новый полис · Сменить ответственного · Приложить ссылку на оплату · Прикрепить документы · Посмотреть полис · История статусов `[ВИ-ФТ-7]`.
Поддержка может **сменить № полиса и подгрузить новый полис**, видимый агенту `[ВИ-ФТ-6]`.

## 2. Расторжение `[ист: раздел «Расторжение полиса»]`

**Форма:** кто заявитель + причина расторжения + документы `[Р-ФТ-1]`.

**[Ф] Статусная модель расторжения** `[Р-ФТ-2]`:
```
Новый → В работе → Ожидаем документы → (Документы загружены — системный) → Готово
                                                                            → Отказ
```

**[Ф] Калькулятор возврата премии** `[Р-ФТ-4]`:
```
Сумма к возврату = (Премия − 0.23 × Премия) / дней действия полиса × дней остатка до окончания
```
(удержание 23% + пропорция неистёкшего срока). Дублируется в [07 §6](./07-payments.md).

**[Ф] Карточка задачи** `[Р-ФТ-3]`: № полиса · СК · Дата · Страхователь · Собственник · **Сумма к возврату** · Причина расторжения · Комментарий/действия агента · Заметка ТП · Статусы.
Кнопки: Сменить ответственного · Прикрепить документы · Посмотреть полис · История статусов.

## 3. Урегулирование убытка (УУ) — Claims `[ист: раздел «Урегулирование убытков»]`

**Форма:** кто заявитель + запрашиваемые документы `[УУ-ФТ-1]`.

**[Ф] Статусная модель УУ** — самая сложная, с веткой **претензии** `[УУ-ФТ-2]`:
```
Новый → Проверка документов → На рассмотрении → Ожидаем документы → Документы загружены
      → Подписание соглашения → Соглашение подписано → Урегулирован

Ветка претензии (кнопка «Оставить претензию» [УУ-ФТ-3]):
      → Направлена претензия → Претензия на рассмотрении → Ожидаем документы по претензии
      → Документы загружены → Подписание соглашения по претензии → Соглашение подписано
      → Претензия урегулирована
```

**[Ф] Карточка задачи УУ** `[УУ-ФТ-4]`: № полиса · Дата страхования · СК · Страхователь · Марка/модель ТС · Собственник · Дата заявления · **Тип убытка · Признак убытка · Тип осмотра** · Комментарии/действия агента · **№ убытка · Дата соглашения СК · Дата соглашения от агента · Дата оплаты · Сумма выплаты** · Заметка · Статусы.
Кнопки: Сменить ответственного · Прикрепить документы · **Прикрепить соглашение · Претензия** · Посмотреть полис · История статусов.

> Это полноценный **FNOL → урегулирование → выплата** (и досудебная претензия). В прототипе `loss` сведён к тем же 6 общим статусам — вся специфика убытка (тип/признак/осмотр/соглашение/выплата/претензия) отсутствует. Крупная дельта для Claims-контекста.

## 4. Раздел «Мои заявки» (для техподдержки) `[ист: ФТ-5, ФТ-6, ПИ-3]`

**[Ф] Поля таблицы:** № заявки · Дата создания · Вид заявки · № договора · Страхователь · **Объект страхования · Регион · Агент · Ответственный** · Статус · Комментарии.
**Фильтры/поиск** `[ФТ-6]`: Период · Вид заявки · Ответственный · Регион · СК · Статус; поиск по ФИО/№ полиса/№ заявки.

**[Ф] Прогресс для агента** `[ФТ-8]`: № заявки · Вид процесса · Дата · Статус · Комментарий · Действие. Кнопка **«Показать историю статусов»**.

**[Ф] Цветовое кодирование** `[ПИ-8]`: промежуточные статусы — **жёлтый**, «Готово» — **зелёный**. Обновление в реальном времени без перезагрузки.

## 5. Сводная таблица статусных моделей (легаси)

| Процесс | Полная цепочка статусов (легаси) | В прототипе |
|---------|----------------------------------|-------------|
| **ВИ** | Новый · В работе · Ожидаем документы · **Ожидаем оплаты** · Готово · Отказ (+ системные: Документы загружены, Оплачен) | submitted · checking-docs · in-work · awaiting-docs · done · rejected |
| **Расторжение** | Новый · В работе · Ожидаем документы · Документы загружены · Готово · Отказ | те же 6 |
| **Убыток** | Новый · Проверка документов · На рассмотрении · Ожидаем документы · Документы загружены · Подписание соглашения · Соглашение подписано · Урегулирован (+ ветка претензии, 6 статусов) | те же 6 |

**Вывод:** прототип использует **единую упрощённую модель из 6 статусов на все три процесса**. Легаси — **три разные модели**, у убытка со ступенями соглашения/претензии и денежными полями. Для V1 нужно решение: хранить полные модели (правильно по домену) или маппить на упрощённые (проще UI). См. [12](./12-gaps-vs-prototype.md), [13, Q12](./13-open-questions.md).

## 6. Пользовательский сценарий подачи `[ист: §1.1.3]`

```
1. Авторизация → «Мои клиенты» → поиск договора → открыть договор
2. Подраздел «Процессы» → выбрать тип процесса → «Продолжить»
3. Выбрать причину (свои причины на каждый процесс) → приложить документы → комментарий
4. Заявка появляется в «Процессах» договора → прогресс + «Показать историю статусов»
5. Для убытка — доп. кнопка «Оставить претензию»
```

## 7. Исключения (Коберн)

| Ситуация | Что в легаси | Риск/требование |
|----------|--------------|-----------------|
| **Ошибка отправки заявки** | Сообщение «попробовать снова» `[ФТ-3]` | Не терять заполненную форму при обрыве 3G; идемпотентность создания заявки (не плодить дубли) |
| **Ожидаем оплаты (ВИ)** | Поддержка прикладывает ссылку на оплату | Оплата доплаты за изменение — снова Billing/идемпотентность [07] |
| **Отказ** | Терминальный статус | Понятный агенту текст, что делать дальше (подать заново) |
| **Претензия по убытку** | Отдельная ветка | Длинный асинхронный процесс; уведомления критичны |
| **Зеркалирование в 1С/вендор** | — | Заявка живёт и в нашей системе, и на стороне СК; синхронизация статусов (память `project_process_visibility`: вкладку заявок в «Сообщениях» НЕ делать) |
