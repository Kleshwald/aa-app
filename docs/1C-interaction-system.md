# Система взаимодействия 1С — как встроить под наши задачи

**Статус:** проработка · 2026-07-22 · в связке с развилкой платформы ([DECISION-frontend-platform.md](./DECISION-frontend-platform.md))
**Что это:** встроенная в платформу 1С:Предприятие подсистема коллаборации — мгновенные сообщения, файлы, аудио/видеозвонки (2 участника), демонстрация экрана, уведомления, **обсуждения, привязанные к объекту базы**. Если кабинет агента строится на 1С 8.5, СВ — **родной ответ на нашу боль №1 (чат)** без внешнего вендора.

> Почему это важно для нас: сейчас чат-бэкенд не выбран (152-ФЗ, спайк на Webim — см. память `project_messaging_architecture`). На 1С этот вопрос закрывается платформой — но с оговорками ниже.

---

## 1. Что даёт СВ (факты платформы)

- **Обсуждения** между пользователями: сообщения, файлы, поиск (Elasticsearch), уведомления.
- **Контекстное обсуждение объекта** — привязано к конкретному объекту базы (договор, заявка, клиент); **ровно одно на объект**; участники — только те, у кого есть доступ к объекту.
- **Внешние участники** — можно вести обсуждение с человеком **без доступа к базе** (клиент, кандидат). → СВ покрывает не только внутренние чаты, но потенциально и агент↔клиент.
- **Видеозвонок — только 2 участника** + демонстрация экрана.
- **Сервер взаимодействия:** либо облачный **1С:Диалог** (на инфраструктуре 1С), либо **свой сервер** в своей сети (Windows/Linux). Свой = конфиденциальные сообщения не выходят наружу. Состав: сервер + Hazelcast (сессии/очереди) + Elasticsearch (поиск).

## 2. Как встроить под НАШИ задачи (рекомендация)

| Наша задача | Механизм СВ | Комментарий |
|---|---|---|
| **Чат агента с поддержкой** («Сообщения») | обычное обсуждение агент ↔ пользователи поддержки | заменяет внешний вендор чата, если мы на 1С |
| **Куратор** (именной, вдолгую) | отдельное обсуждение агент ↔ куратор | тот же механизм, другой участник |
| **Переписка по процессу** (изменение / расторжение / убыток) | **контекстное обсуждение объекта** — прикреплено к договору/заявке | ⭐ ключевое: переписка живёт ВМЕСТЕ с заявкой, а не в отдельном силосе (наш принцип «история = вход в заявку», память `project_process_visibility`) |
| **Сигнал «Ждут ваших действий»** | **уведомления СВ** («страховая ответила») | нативный источник события для сигнала (`project_attention_signal`) |
| **Агент ↔ клиент** | **обсуждение с внешним участником** | возможно, но с оговорками (см. §3): согласие на ПДн, модерация, лимиты внешнего участника |
| **CRM-слой** | объекты 1С (клиент/договор/задача/напоминание) + СВ поверх | не изобретать: история взаимодействий, задачи, напоминания по клиенту = CRM на объектах; для полного CRM — конфигурация **1С:CRM** со своей интеграцией СВ |

**Главная идея встраивания:** не делать «ещё один чат-раздел», а **распределить СВ по объектам**:
- глобальный чат поддержки/куратора — в разделе «Сообщения» и в панели взаимодействия (правая панель, иконка с счётчиком непрочитанного);
- переписку по процессу — **контекстным обсуждением прямо на форме договора/заявки** (кнопка «Обсудить»), чтобы агент отвечал клиенту «где заявление» не выходя из карточки;
- уведомления СВ — питают сквозной сигнал «Ждут ваших действий».

## 3. Честные ограничения (не подыгрываем картинке)

1. **Хостинг сервера = развилка 152-ФЗ.** Переписка по убытку содержит обстоятельства события и документы — это ПДн и чувствительные данные. → сервер взаимодействия **свой, в РФ** (не облачный 1С:Диалог, где данные уходят на инфраструктуру 1С). Это операционная нагрузка: кластер Hazelcast + Elasticsearch, администрирование, отказоустойчивость.
2. **Пользователи СВ = пользователи базы** (кроме внешних). Массовый чат тысяч агентов → тысячи пользователей → снова упирается в **лицензии** — ту самую цифру, что может убить экономику 1С (см. `project_platform_fork_1c85`, RAT-2). СВ не отменяет лицензионный вопрос, а усиливает его.
3. **Внешний участник (клиент) — отдельный механизм** (приглашение/доступ извне), со своими лимитами и требованием **согласия на обработку ПДн**. Не «просто чат с клиентом».
4. **Видеозвонок — 2 участника.** Для «агент+клиент» ок, для групповых разборов — нет.
5. **Контекстное обсуждение — одно на объект, участники = у кого доступ.** Нужна аккуратная модель прав: агент не должен видеть переписку по чужому договору; куратор/поддержка — по своей зоне.
6. **Модерация и хранение.** Финансовый/страховой контур → аудит переписки, сроки хранения, выгрузка по запросу.

---

## 4. Вывод

СВ — сильный аргумент **за** 1С по чату и по переписке-в-контексте-объекта: то, что мы в вебе решаем внешним вендором и спайком, здесь даётся платформой и кладётся прямо на договор/заявку. **Но** она не снимает два наших главных риска по 1С — **лицензии на масштабе** (даже усиливает) и **152-ФЗ-хостинг** (требует свой сервер в РФ). Правильный порядок: сначала письмо про лицензии (RAT-2), и только если экономика проходит — СВ становится крупным плюсом дизайна.
